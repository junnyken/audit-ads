## 7. Chosen designs

**Topology.** Versioned Compose production overlay supporting both a managed platform
(Coolify / Vibe Host terminating TLS) and a self-managed VPS (optional `edge` nginx profile).
Chosen because the audit could not confirm which target will be used, and because guessing one
would produce artifacts that only work there.

**Dispatcher scheduling: Option 3 — a dedicated bounded container.** systemd is not running in
this workspace and no crontab exists, and neither Coolify nor Vibe Host gives host-unit access:
a container is the only mechanism that works on all three targets. One pass at a time, batch 10,
`sleep` between passes, stop signal honoured in one-second slices, every pass recorded.

**Environment and secrets.** Runtime-injected from a file outside git (or the platform's secret
store), never baked into an image. `.env.example` keeps names only. Production configuration is
validated at startup and refuses to boot when unsafe.

**Backup/restore/rollback.** `pg_dump` + gzip + SHA-256 + JSON metadata, verified by **content**
(table count and `alembic_version`) rather than by size alone; restore drills into an isolated
database and drops it; rollback is application-only, and a real restore is deliberately not
scripted.

**Observability.** One new additive table (`operational_runs`) plus host metrics read from
`/proc` — **not** the Docker socket, which would hand whoever compromises the API control of
the host.

**Test send.** Preview and execution behind four independent gates, keyed separately from the
alert outbox, creating no alert and mutating no A1/A2/A3 record.

## 8. Declared change to an existing behaviour

`GET /api/v1/system/status` previously returned `worker_status: "not_configured"` unconditionally.
A4 adds a dispatcher, so that constant would become a lie. It is now derived from recorded runs:
`running` / `stale` / `not_configured`. Declared here before implementation; a test covers both
states.

## 9. Stage separation

**Stage A (this work, no external side effects):** artifacts, validation, tests, a local
staging-equivalent runtime verification, and fully written runbooks.

**Stage B (not started, requires separate approvals):** deploying to a target, and sending a
real Telegram message. Two separate approvals; one does not imply the other.
